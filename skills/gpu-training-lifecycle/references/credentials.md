# Credentials across the reusable training lifecycle

Use this at the point a stage actually needs access. Reuse valid, authorized credentials; a new experiment does not require new keys. No credential setup or cloud action is authorized merely by loading these skills. Guidance checked against official documentation on 2026-10-01; verify actual host, service and installed versions before giving exact setup steps.

## Small repeatable flow
1. Identify the next operation, service/account/project, verified endpoint and consumer (user's client, controller, builder, worker or replacement worker). Determine whether it can work anonymously. Ask for ordinary routing information only if unavailable; do not request every possible credential up front.
2. Check the existing authorized identity and needed scope with a harmless identity/metadata read, without printing tokens or full environment/config files. Verify destination ownership/TLS and account first; never send credentials to a guessed endpoint, untrusted redirect, or unrelated service. Authentication success alone does not prove project/bucket/repository permission.
3. If missing, expired or insufficient, explain just the missing capability, minimum resource scope, where the user should configure it in the actual execution environment, and the check that will follow. Link the verified official setup page. Do not invent a vault widget, secret UI, CLI option or login capability the environment lacks. New credentials/grants, persistent access setup, permission expansion, rotation or revocation require the applicable confirmation; credential entry/transmission follows the host's secure user-handoff rules. The user enters secrets directly in the verified service/secure flow, never chat or an uploaded key file here.
4. After the user reports completion, recheck identity and the exact target read. Report ready/blocked accurately. A read check cannot prove write permission; use permission inspection where supported and perform a tiny write/delete probe only under explicit scope, with its own isolated object and no checkpoint overwrite.
5. Wire only needed access through the approved runtime mechanism, then test the same path on replacement workers during authorized stack qualification. Record identity/scope/readiness/expiry metadata, never secret values. Normal runs use fast checks; do not rebuild images or rerun all setup.
6. At finish, preserve approved reusable authentication. Remove only run-owned temporary access covered by explicit cleanup authority, after checking dependent jobs/controllers. Do not automatically revoke long-lived keys, log out shared accounts, delete credential stores or break another run. Discard ephemeral worker-local material under the approved lifecycle; rotation/revocation is a separate security action.

## What each consumer needs

| Access | Where needed | Minimum intended scope and readiness check |
|---|---|---|
| Provider and managed SkyPilot | Approved client/control plane, not general training code | Correct provider tenant/project and scheduler endpoint; only provision/query/stop capabilities required by the approved campaign. Inspect exact version/account and existing identity; never forward an administrator credential to workers just because the controller has it |
| Dataset storage | Preprocessor and training/replacement workers that fetch data | Read only for exact immutable dataset bucket/prefix/version; list only where the adapter requires it. Read a representative manifest/object. No dataset write or account-wide storage access for training |
| Checkpoint storage | Publishing/restoring worker plus necessary controller metadata reads | Read/list/write only for the run prefix, plus actual multipart/conditional-write operations the adapter needs. Do not grant deletion unless retention/cleanup requires and authorizes it. Separate retained storage from worker lifetime; validate replacement identity/access |
| Metrics tool (W&B, MLflow server, ...; none if not used) | Rank-zero training/replacement process, and an authorized observer if needed | Approved endpoint, project/run identity (W&B: entity/project and stable run ID); authorized metrics only. Deliver the existing runtime key through the approved mechanism. Confirm identity/project access without creating a run or uploading telemetry solely as an auth test; run creation/logging needs its own task scope |
| Hugging Face | Only consumers of private/gated model or dataset revisions | Anonymous public downloads first where supported; no write token for read-only training. A SkyPilot `hf://` mount of a private or gated dataset needs the token on the SkyPilot API server host (SkyPilot reads `HF_TOKEN` or the HF token file there and passes it to the cluster); on a server the user does not run, the loader reads it from the launch's secrets instead; training code that downloads it itself gets `HF_TOKEN` through the launch's secrets file. Never in the task or the image |
| Notification channel | The training worker (`notify.py`), and the campaign guard's notify command when it runs | `NOTIFY_URL` (and `NOTIFY_FORMAT`) in the launch's secrets file: a topic or webhook URL is a credential, since anyone holding it can post. Check it once with `notify.py --strict` from the operator's machine before the launch. Never in the contract, the task or the image |
| Container registry | Builder publishes; worker host/runtime pulls before training | Builder push to the approved repository, worker pull only for the pinned artifact. Public pulls may need no credential. Validate manifest access. A secret injected inside the training container cannot authenticate the earlier private-image pull; configure the approved launcher/host mechanism separately |

Prefer supported scoped/short-lived workload identity to copying broad static keys, but do not create or expand it implicitly. Actual role names and APIs are provider/version-specific; this table describes needed capabilities rather than inventing IAM roles. A least-privilege proposal is not proof the currently configured principal has only those rights.

## Runtime and replacement safety

Keep secret values out of image layers/build arguments, repositories, experiment JSON, task YAML, chat, logs, screenshots, shell history and CLI argument values. Disable shell tracing and sanitize diagnostic output; environment variables can still be read by privileged processes and are not a universal vault. Store reusable credentials only in the user-approved service/helper with verified access controls. Avoid persistent login side effects when a runtime identity suffices.

Current SkyPilot docs distinguish non-secret `envs` from `secrets`, support required null placeholders and name-only forwarding from an existing environment. These are version-dependent mechanisms, not permission to transmit a key; confirm actual client/server support, API-server storage/access behavior and the approved trust boundary. Do not place values into generated YAML or call forwarding tools without the required authorization. If unsupported, ask for an actually available secure mechanism rather than reverting to plaintext configuration. Dashboard redaction does not guarantee application logs or backups are secret-free. [SkyPilot environment variables and secrets](https://docs.skypilot.ai/en/latest/running-jobs/environment-variables.html)

A replacement must reacquire required data/checkpoint/registry/metrics-tool access without relying on files that existed only on the lost worker. Record how an approved refreshable identity or protected secret reference is delivered, expected expiry versus run/recovery duration, and who resolves expiry. Keep controller authentication separately protected. Cloud credentials on VMs follow SkyPilot's documented defaults: this is a research workflow, not a hardened system. By default SkyPilot copies the API-server machine's cloud credential files to each VM it launches (and on AWS and GCP also attaches its own instance role), which is what lets a cluster autostop/autodown itself and a controller VM launch workers. Keep that default unless the user asks for hardening; SkyPilot's `remote_identity` options (a service account or custom role, or `NO_UPLOAD`) are documented per cloud in its [config reference](https://docs.skypilot.ai/en/latest/reference/config.html). If you change it, confirm in the first run that autodown and managed-job recovery still work. Training code gets the storage/registry/metrics-tool secrets it needs through `secrets:` or an equivalent runtime channel, never through task files or images. Unattended recovery needs controller credentials that outlive the run's worst-case recovery window: an interactive CLI login token (often valid for hours) is unsuitable; use a service-account credential on the control plane, set up as SkyPilot's cloud-setup page for the provider describes. Missing/expired access pauses admission or the affected operation with bounded retry and a clear setup request. It never authorizes a fresh training start, a new metrics run, wider permissions, another provider or on-demand fallback. Apply the declared metrics-tool outage policy without weakening checkpoint requirements; stop expensive idle retries within the approved budget/timeout policy.

## Non-secret readiness record

When useful, keep one row per required access: purpose, consumer, provider/account/project, verified endpoint (no userinfo/query credentials), resource scope, authentication mechanism name, readiness (`not_needed`, `ready`, `missing`, `expired`, `insufficient`, `unknown`), last checked time, known expiry, replacement delivery status, reusable versus run-temporary, and next user action. Do not include token material, key files, signed URLs, credential hashes or authentication headers. This record is evidence, not authorization or a secret store. A concise missing-items checklist is sufficient; no new framework is required.

## Official setup references (follow only when needed)
- The chosen provider's page under [SkyPilot cloud setup](https://docs.skypilot.ai/en/latest/cloud-setup/cloud-permissions/index.html), and the provider's own SkyPilot guide if it has one: select the appropriate existing account/control environment. Service-account generation examples are security-changing actions, not automatic preparation.
- [SkyPilot API server](https://docs.skypilot.ai/en/latest/reference/api-server/api-server.html): login can persist endpoint/authentication configuration. Use the verified service and supported secure entry; never embed passwords in endpoint URLs, with one exception: a server whose documented login is basic auth with the password in the URL. The user then types `sky api login` in their own terminal; the agent never prints `~/.sky/config.yaml`, reads `sky api info` only through the redaction filter (controller runbook) and records the endpoint without user or password. Commands can start a local API server if none is connected, so check that behavior first.
- [W&B authentication example](https://docs.wandb.ai/models/integrations/metaflow): confirms runtime API-key authentication. Read the actual W&B account/deployment instructions; do not paste its sample `export KEY=value` into shared history or generate a replacement key unnecessarily.
- [HF token scope](https://huggingface.co/docs/hub/en/security-tokens) and [HF CLI identity check](https://huggingface.co/docs/huggingface_hub/en/guides/cli#hf-auth-whoami): use read/resource scope when required; public access does not justify collecting a token.
- [Docker login and credential helpers](https://docs.docker.com/reference/cli/docker/login/): inspect the actual credential-store behavior before a requested login; base64 config is not encrypted storage. Do not install/change helpers or log out shared credentials without applicable permission.
