# Operating model

Where things run, what runs them, and how a stack is built, qualified and continued. Contents: execution scope; build once and reuse; qualify a new stack once; code dev loop; operating model; CPU work off rented GPUs; fixed execution and responsibilities. Gates before a launch: [gates.md](gates.md).

The output is a project-specific deterministic workflow, reviewed once and operated by normal processes. Do not require a continuously running AI agent to inspect logs and decide when to checkpoint, retry or resume. These skills and offline helpers do not themselves install that runtime. Inspect the actual training repository before implementing its adapters; there is no universal working callback for every framework or data loader.

## Supported execution scope
This suite targets one node with up to eight GPUs on cloud VMs launched by SkyPilot. Kubernetes and Slurm backends, through SkyPilot or directly, are out of scope: their spot, region, storage and identity models differ. Flag larger or distributed scope rather than silently applying these defaults. The helpers assume NVIDIA GPUs (CUDA, `nvidia-smi`); AMD ROCm and TPUs are not covered. Research frameworks and libraries are not restricted: PyTorch, JAX, Hugging Face, DeepSpeed or anything else, as long as the choice is pinned in the image and its checkpoints can be inventoried (`gpu-training-recover` → `references/framework-mapping.md`).

## Build once and reuse
1. Freeze code, dependencies, container digest, data identity, storage and placement contract. Pin the researcher's chosen framework, libraries and metrics tool (W&B or another) in the image; prepare data and build on CPU infrastructure; on CPU check only what runs in seconds (argv parse, imports).
2. Qualify the actual GPU/framework/data/checkpoint stack once under a bounded approved pilot. Save compatibility tuple and evidence; material changes invalidate relevant tests.
3. Write the project's container entrypoint ([entrypoint.md](entrypoint.md)): framework save/restore integration, run journal and commit calls. The bundled helpers do the rest: the renderer, the GPU preflight, the checkpoint marker (publisher and selector) and the campaign guard. Do not label the entrypoint implemented until the GPU qualification task ran it.

## Qualify a new stack once
For a new software/hardware/storage stack (image, framework, provider, storage mode or SkyPilot version), qualify once, each step cheap before the next:
1. **In the image, on CPU** (image runbook): parse the exact training argv with the framework's own parser and import the project. Seconds; it catches a removed or renamed option before anything is rented. Nothing heavier runs on CPU: fresh start, resume, stop and finalize are proven on the GPUs.
2. **One GPU qualification task** (`render_job.py --variant qualify`) on the approved GPUs and world size, with the real image and bucket mounts, on the qualification subset (data skill). Commands: `gpu-training-launch` → `references/runbook.md` §1; what the entrypoint does in it: `qualify` in [entrypoint.md](entrypoint.md#behaviour-by-run_mode). It proves what tests on local directories cannot (mount semantics, first-run writes, selection and restore through the framework) and measures what sizes the main run.
3. **CPU rehearsal** (`--variant rehearsal`), only when GPU time is unaffordable or unavailable: the same two starts on a small CPU VM. It proves storage and resume wiring, nothing about the GPU path.
Fix failures with another qualification task, never by launching the managed job to see what happens. Save the tested compatibility tuple and evidence (`qualification.json`). A qualified stack skips this: each allocation performs only the job-start preflight and selection. Repeat qualification only for material image/framework/kernel/GPU topology/data adapter/checkpoint-store changes or an actual regression. A deliberate worker interruption (a drill) is a tool for developing these skills, not a step of a run.

## Code dev loop
Getting the training code right is development, not qualification. Do it on a GPU the user owns when there is one (asked at intake; it must run the same code path: the image's platform and precision). Otherwise a failed qualification keeps its cluster, and each fix runs there as a new qualification task with `sky exec --workdir <project>` (the fix loop, launch runbook step 1): the code is copied into the container where `run:` starts, mounts and data stay, no image rebuild, a minute or two a round. Then rebuild the image once (code layer last, so the rebuild and pull are small) and run the qualification task on the baked digest. Code copied by `sky exec` never reaches a paid or recovery run. A CPU pass never qualifies a multi-process or GPU fix, and the control host is not a training machine.

## Operating model: where things run and what runs them
- **Operator machine (laptop):** only to create the control host and to SSH into it. Run the controller skill's `scripts/net_check.py` first: a VPN or proxy that relays SSH breaks SkyPilot's readiness probe for VMs launched from the laptop.
- **Control host** (a small always-on CPU VM, a different region is fine if the GPU region has no CPU quota): SkyPilot API server, the guard, builds, data preparation and every runbook below. Long stages run detached through the controller skill's `scripts/stage.sh` (log and exit code survive an SSH drop). Provider-specific operations go through the project's provider hooks ([provider-hooks.md](provider-hooks.md)).
- **Runbooks, not orchestration code.** Each stage skill has a `references/runbook.md`: exact commands with a check after each step (controller: control host; image: build and push; launch: secrets file, qualification, submit and guard; observe: wait, milestones and triage; recover: restore rules; finish: verification and inventory). `sky` commands follow the version chosen at the start and the official `skypilot` skill. Code is kept only where it runs unattended or checks deterministically: the campaign guard, the checkpoint helpers, the validator, the renderer (with the start check), the cost calculator, the GPU preflight, `net_check.py` and `stage.sh`. The agent runs the runbooks and decides at the approval points.
- **Waiting:** wait for notifications, never poll; waits and quality checks: observe runbook.
- **Order of a first run:** selection (the setup envelope) → control host → in parallel {data, image build and push (with the entrypoint and the recover skill's resume wiring), provider hooks and secrets script} → the GPU qualification task → approval → submit and guard → wait → finish. A repeat run on a qualified stack: start the control host → refresh quote and quota → approval → submit and guard → wait → finish.
- **Continuing an existing project:** the stages are entry points, not a sequence. Read what the project already holds (contract, image digest, data manifest, `qualification.json`, control host, checkpoints and `FINAL.json`, campaign ledgers), use it, and check only what the requested step depends on (the validator and the renderer do this for a launch). A stage is redone when one of its inputs changed: the user says what changed, the recorded identities (commit, digest, data version, the qualification tuple) confirm it. A stopped run resumes under its run id; changed code or configuration is a new run revision that starts from step 0 (the fork path is deferred). The same holds in every interaction level.
- **Entrypoint:** project code following the [entrypoint contract](entrypoint.md) (inputs, `RUN_MODE`, journal, commit line, exit codes, every tunable in argv).

## Keep CPU work off rented GPUs
For image builds, asset/dataset downloads and preprocessing, ask which machine the user has: their Linux CI, a CPU VM in the training region, a remote builder, or a GPU workstation they own (not rented). A Mac-only user can use hosted Linux CI or rent a small CPU VM for this. Match the image platform to the target host CPU (Grace-based GH200/GB200/GB300 are arm64). Report the unavoidable startup minutes of rented GPU allocations (image pull, prepared-data fetch, fail-fast job-start preflight). Unit tests of the training code are the project's own development practice, never a pipeline stage or a stand-in for the GPU qualification task (or the optional CPU rehearsal) against the real bucket.

## Fixed execution and responsibilities
- **Provider:** allocates GPU compute and separately retained persistent storage. Worker termination must not delete checkpoint truth.
- **SkyPilot or approved scheduler:** launches/reacquires the fixed-provider worker and runs the same immutable container. Infrastructure recovery alone does not restore training state.
- **Container entrypoint:** performs fast identity/device/access checks, sets a per-start `CHECKPOINT_ATTEMPT` tag for checkpoint directories, selects the newest committed checkpoint that verifies (`checkpoint_marker.py select --mount-root /checkpoints`, which blocks if the bucket is not mounted) and restores it through the actual training API before any update. It never rebuilds the stack at each boot.
- **Training loop/callbacks:** coordinate all ranks at an optimizer boundary, save full training/data/RNG state into the SkyPilot checkpoint mount, await save completion, then commit (manifest, verify, `COMMITTED.json` last). Timed/SIGTERM saves are supplementary; periodic durable saves must work without notice.
- **Stall watchdog:** the observe skill's `scripts/progress_watch.py` wraps the launcher and ends a silent job (`STALL` line, stacks, exit 93); how it judges silence: `gpu-training-observe` → `references/guard.md#stall-watchdog`; the ticks: [entrypoint.md](entrypoint.md).
- **Durable progress/selector:** COMMITTED markers in the checkpoint bucket own progress; a managed job has one writer, so no coordinator or fencing is needed. Only positively missing/incomplete/corrupt candidates permit fallback under latest-complete; auth/network/compatibility uncertainty blocks or retries the same read within bounds. No valid checkpoint after known progress is a terminal blocked condition.
- **Metrics tool in rank zero (W&B or the researcher's choice):** reports authorized metrics using stable run identity and separate training/global_step and history ordering; it does not store authoritative recovery state or decide training completion.
- **Campaign guard (Standard tier):** the observe skill's `scripts/campaign_guard.py` (or an equivalent the user already runs) on an always-on host independent of the worker: enforces an upper-bound spend at the on-demand ceiling (the hard stop), infrastructure attempts, capacity wait and a deadline when one is set; persists its ledger across restarts; cancels only the job it tracks; notifies the user, including when it cannot observe the job. A helper decision output alone is not this service.
- **Worker-side bounds:** the renderer wraps the managed task's argv in `timeout` of the budget's runway at the ceiling, so an allocation stops by itself even if the guard and controller are both down (exit 124 ends the job; a recovery starts a new allocation and a new timeout, so the guard bounds the total). With a deadline (optional, none by default) the entrypoint also reads `CAMPAIGN_DEADLINE_UTC`, refuses to start after it, and at the first checkpoint boundary past it publishes a final checkpoint, records `deadline_stopped` in the run journal and exits 0, so spending stops even if the guard and controller are both down.
- **Completion/export script:** commits final state, verifies requested outputs, marks outcome, terminates authorized exact compute IDs, and reports separately retained storage/control costs. It never deletes the only recoverable artifact to make a cleanup indicator green.

State transitions are explicit: uninitialized → running → checkpoint committed → recovering → running → final committed → terminal/reconciled. Unknown status means reconcile original identities; it never means submit a duplicate. First-ever fresh initialization requires an explicit uninitialized run policy; recovery never silently creates a new experiment. Report missing project components rather than filling gaps with an AI-dependent promise.
